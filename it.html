지도 검색 없이,
거리와 균등을 함께 만족하는 자동 배정

기존 Java + Oracle 시스템의 코드를 수정하지 않고, 엔진이 신청 테이블을 DB 폴링으로 감시하고, 균등은 제약·거리는 목적으로 분리해 선정하며, 확정 단계의 정합성은 FOR UPDATE + 유니크 제약으로 DB 수준에서 보장합니다.

이 프로젝트를 이렇게 이해했습니다

현재 공고와 이전 공고(157444)를 함께 분석해 도출한 세 가지 접근 방식입니다.

INSIGHT 1 · 연동

DB 폴링 무접촉 연동

기존 시스템의 코드를 수정하지 않고 신청 테이블을 감시해 연동합니다. 기존 개발사의 협조에 대한 의존도를 낮추는 차별화 포인트이자, 최고점 리스크 R1(협조 지연)의 직접 완화책입니다.

INSIGHT 2 · 알고리즘

균등=제약, 거리=목적

균등 배분은 허용 편차 제약으로, 거리 최소화는 목적 함수로 층위를 분리합니다. 묶음 반경·허용 편차·가중치는 ENG_PARAM 설정값 — 규칙 조정이 재배포가 아닌 값 변경이 됩니다. 배정 실행은 일 1~2회 배치가 기본안입니다.

INSIGHT 3 · 검증

시뮬레이션 검증 2주 · 조정 3회

과거 수기 배정 데이터로 배정 결과를 재현·비교하는 시뮬레이션 리포트로 "조정 반복"을 저비용화합니다. 공고의 제안 요청(검증 방법·조정 기간)에 대한 직접적 답이며, "조정은 계약 범위" 조항의 서면 실행 기준이 됩니다.

01 · CORE

배정 자동화 파이프라인

선별 → 좌표 → 묶음 → 선정 → 확정, 5단계 배치 한 회전으로 수기 검색·입력을 제거합니다 (EPM 유스케이스 11~15 · assign1001)

각 단계를 클릭하면 상세 설계(규칙 코드·접근 테이블)가 우측 패널에 표시됩니다.

공고 수용 기준 4건 — 설계로 이렇게 대응합니다

수용 기준 1

"신청 건이 접수되면 담당자 조작 없이 배정이 확정되고 기존 시스템에 반영된다"

스케줄러 일 1~2회 배치가 폴링→확정까지 무인 수행. 단, 2~3건 묶음 요구와의 긴장 관계로 실행 시점은 착수 합의 1번 안건 (→ INSIGHTS)

수용 기준 2

"배정 확정 직후 홈페이지의 기존 조회 화면에서 해당 기업이 조회된다"

기존 배정 테이블(EXT_ASSIGN 가칭)에 INSERT/UPDATE — 커밋 즉시 기존 화면이 읽음. 기록 스펙은 데이터 매핑 정의서로 기존 개발사 확인 (M2)

수용 기준 3

"같은 도 안에서 전문가별 배정 건수 차이가 합의된 허용 범위 안에 유지된다"

허용 편차를 하드 제약으로 강제 + 커밋 직전 편차 재검증(위반 시 롤백·대기) + ENG_COUNTER를 FOR UPDATE로 갱신 — 어긋난 확정이 DB에 남지 않음

수용 기준 4

"배정 불가 건이 대기 상태로 남고 확인할 수 있다"

WAITING 전환 + 사유 코드(GEOCODE_FAIL / NO_CANDIDATE / DEVIATION_BLOCK) 기록, 대기 목록 API·CSV 제공 (assign1002) — 화면 없이도 운영 가능

무검수 자동 확정 → 회수(recall)·근거 이력이 필수 안전장치 운영 테이블 ALTER 0건 — 신규 데이터는 전부 ENG_* 격리

03 · ENGINE

균등 제약 · 거리 목적 선정 엔진

"거리와 균등이 충돌할 때" — 가중합으로 섞지 않고 층위를 분리합니다 (RSM DistributionRegulator · BS0034~35, BS0038)

§7-1 · 최우선 영향: 엔진 아키텍처 전체 · 일정 ±1주

배정 실행 시점 — 즉시 확정 vs 2~3건 묶음의 긴장

수용 기준 "접수되면 …확정"은 즉시성을 암시하지만, 근접 기업 2~3개 묶음은 묶을 상대가 모일 시간이 필요합니다. 즉시 배정하면 묶음 상대가 아직 없는 건이 생깁니다.

묶음 품질 최상 · 구현 단순 · 조회 반영 최대 반일 지연. 스케줄러 @Scheduled + ENG_JOB_RUN 잠금으로 단일 실행 보장. 기본안으로 제안 — 착수 워크숍 1번 안건.
반영 빠름 · 묶음 대기 창 N시간의 상태 관리 복잡도 증가(만료 처리·부분 묶음). 필요 시 배치 기본안에서 상향 협의하는 옵션 경로로 분리.
§7-9 영향: 연동 구조 · 3자 협조 의존도

신청 인지 방식 — API 호출 vs DB 폴링

1차 공고(157444)는 기존 사이트가 배정 API를 호출하고 그 수정은 발주처 담당이었습니다. 이번 공고는 언급이 없습니다 — 결정에 따라 기존 개발사 협조 의존도가 달라집니다.

기존 시스템 코드 수정 0건 — 개발사 협조가 "스키마 정보 제공"으로 수렴. 최고점 리스크 R1의 직접 완화. 폴링 주기=배치 주기라 실시간성 손해도 없음.
실시간성은 높지만 기존 시스템 수정 + 기존 개발사 작업·배포 일정에 종속. 1차 공고 시점 "소스 이관 중" 정황을 감안하면 일정 리스크가 큼.
§7-7 영향: 배정 품질 · 검증 반복 횟수

거리 vs 균등 충돌 시 우선순위

공고가 제안사의 접근 방식을 직접 요구한 항목입니다. 두 목표를 어떻게 겹치지 않게 정의하느냐가 조정 반복 횟수를 좌우합니다.

편차 상한이 파라미터 하나로 명시 보장 — 담당자에게 배정 사유를 설명 가능(XAI). 거리 손해는 시뮬레이션 평균·최대 거리로 정량 확인하며 조정.
가중치 w를 정해야 하는데 "편차가 몇 건까지 벌어지는가"를 보장 못함 — 검증 라운드마다 w 재조정이 반복되어 조정 3회 프레임을 위협. 기각.

핵심 결정 기록 (ADR)

ADR-001 · 배정 엔진 언어
Java 17 + Spring Boot 3 — Python·Kotlin 기각

Python+FastAPI는 운영 이질성(기존 Java+Oracle 환경에 이질 스택 추가), Kotlin은 국내 유지보수 인력 풀 제한으로 기각. "추후 유지보수 의뢰" 희망 조건에서 인수인계 리스크 최소가 최우선.

ADR-002 · 신청 인지 방식
DB 폴링 — 기존 시스템 코드 수정 0건

기존 시스템의 API 호출 방식은 개발사 수정·배포 일정에 종속(R1). 폴링 주기=배치 주기이므로 실시간성 손실 없음. 기존 화면과의 접점은 "EXT_ASSIGN 기록 스펙" 하나로 수렴.

ADR-003 · 동시성 제어
3중 방어 — 직렬화 + 잠금 + 제약

① 단일 워커 + ENG_JOB_RUN 함수기반 유니크(RUNNING 1건 — ORA-00001 즉시 차단) ② 고정 순서 FOR UPDATE(CASE→ASSIGN→COUNTER, 교착 방지) + 커밋 직전 편차 재검증 ③ 활성 배정 1건 유니크 + BUNDLE_ITEM.case_id 유니크 — 코드 결함까지 DB가 최종 차단. 분산 락·메시지 큐는 규모상 과잉으로 배제.

ADR-004 · 거리 연산
애플리케이션 레벨 하버사인 — 공간 DB 미사용

공고 전제("지리 연산 전용 DB 옵션 미사용") 준수. 40명 규모 전수 계산은 밀리초 단위. 도로 이동 거리는 IDistanceCalculator 뒤에 격리 — 검증 결과 필요 시에만 +3~5일 옵션으로 교체.

ADR-005 · 규칙 관리
코드가 아닌 ENG_PARAM 설정 파라미터

묶음 반경·허용 편차·실행 주기를 설정값으로 — "조정은 계약 범위" 조항 하에서 조정 1회 비용을 재배포가 아닌 값 변경으로 낮춤. 파라미터 스냅샷을 근거 이력에 함께 기록해 감사 정합 유지(BS0046).
